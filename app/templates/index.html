📖 How it works

Vulnerable code — Python f-string directly in SQL:
sql = f"SELECT * FROM products WHERE name LIKE '%{q}%'" Input ' OR '1'='1 becomes: … LIKE '%' OR '1'='1%' → returns ALL rows.

Secure code — Parameterized query (DB driver escapes the value):
db.execute("SELECT * FROM products WHERE name LIKE ?", (f"%{q}%",)) The ? placeholder is escaped by SQLite — injection becomes a literal string search.

🔒 Account Lockout & Exponential Backoff

After 5 failed logins, the account is locked. Each subsequent lockout doubles the duration (exponential backoff):

1st lockout (5 fails): 5 minutes
2nd lockout (10 fails): 10 minutes
3rd lockout (15 fails): 20 minutes
4th lockout (20 fails): 40 minutes
Max lockout: 24 hours

Progressive delay is also applied per attempt:

attempt 1: +0.5s delay attempt 2: +1.0s delay attempt 3: +1.5s delay attempt 4: +2.0s delay attempt 5: LOCKED → 5 min

Delays slow brute-force without revealing whether the username exists.

🔄 CSRF Protection Lab

Cross-Site Request Forgery tricks a browser into making authenticated requests. This app defends against CSRF with both SameSite=Lax cookies and CSRF tokens on sensitive endpoints.

⚡ How a CSRF Attack Works

ATTACKER's page (evil.com) contains: <form action="https://bank.com/transfer" method="POST"> <input name="amount" value="10000"> <input name="to" value="attacker"> </form> <script>document.forms[0].submit()</script> Browser auto-sends session cookie → Bank executes transfer as victim!

🛡 How This App Defends

Layer 1 — SameSite=Lax cookie
Session cookie not sent on cross-origin POST — the forged form above would send no cookie.

Layer 2 — CSRF Token in X-CSRF-Token header
Every state-changing request must include a token tied to the session. A cross-origin page cannot read this token due to the browser's Same-Origin Policy.
